## ROOT CAUSE (already established — implement the fix, not more research)
Delivery used a **non-atomic pre-send SELECT (`already_sent`) followed by a post-send INSERT (`mark_alert`)**.
The unique-constraint "claim" happened only AFTER the Telegram network call via `mark_alert`'s
`INSERT OR IGNORE`, so a duplicate send could occur and was then masked (alerts table stayed at 3 rows despite
a reported `sent:1` in Run #5). Fix = atomically claim the post_id via the unique constraint BEFORE calling
Telegram, fail closed.

## PART 2 — Atomic delivery claim (db.py + notifier.py)

   `delivery_claims(id INTEGER PRIMARY KEY AUTOINCREMENT, post_id TEXT NOT NULL, channel TEXT NOT NULL DEFAULT 'telegram', status TEXT NOT NULL, claimed_at TEXT NOT NULL, sent_at TEXT, message_id TEXT, error TEXT, UNIQUE(post_id, channel))`
3. Add functions:

   - `complete_delivery(c, post_id, message_id, channel='telegram')`: set `status='sent'`, `sent_at=now`, `message_id=?` where post_id+channel.
   - `fail_delivery(c, post_id, error, channel='telegram')`: set `status='failed'`, `error=?`.
